This page lists the public REST endpoints you can call from scripts, CI jobs, and your own apps. It is for developers who already know what they want to automate and need the exact path, method, and permission.

New to the API? Start with [API authentication](/api/authentication) to get a token, then copy a request from [API examples](/api/examples).

**Base URL:** `https://api.agentruntime.io`

<Note>
  This page covers the stable, customer-facing endpoints. Other paths you may see in browser developer tools belong to the Console and can change without notice.
</Note>

## Before you call an endpoint

Every request needs one of:

- **A personal access token (PAT)**: send `Authorization: Bearer pat_...`. The token already belongs to one workspace, so you do not need to send a workspace header. See [API authentication](/api/authentication).
- **A Console session cookie**: used by the Console in your browser.

### Who can call what

The **Role** column shows the lowest [workspace or project role](/platform/roles-permissions) that can call the endpoint. If you use a PAT, the token's scopes must also allow the call.

| Shorthand | Meaning |
|-----------|---------|
| **viewer+** | `project_viewer` or higher |
| **contributor+** | `project_contributor` or higher |
| **project_admin** | `project_admin` or higher |
| **tenant_admin** | Workspace admin (billing and workspace-level settings) |

### Responses and errors

Successful calls return JSON. Errors return a JSON body like `{ "error": "..." }`.

| Status | Meaning |
|--------|---------|
| `400` | The request is malformed or a required field is missing |
| `401` | Missing or invalid authentication |
| `403` | Your role or the token's scopes do not allow this call |
| `404` | The resource does not exist, or you cannot see it |
| `409` | A conflict, for example `revision_conflict` when you save over a newer version of a workflow |
| `422` | Validation error (workflow graph, bindings, billing) |
| `429` | Rate limited. Wait for the `Retry-After` header, then retry |
| `5xx` | Temporary server error. Retry with exponential backoff |

## Workflows

A workflow has one **Live** copy that you edit and run, plus optional frozen **published versions**. Saving changes the Live copy straight away; you only need to publish when you want a version that callers can pin to. See [Workflow Studio](/workflows/studio).

| Method | Path | Role | Description |
|--------|------|------|-------------|
| `GET` | `/v1/workflows` | viewer+ | List workflows |
| `POST` | `/v1/workflows` | contributor+ | Create a workflow |
| `GET` | `/v1/workflows/{id}` | viewer+ | Get a workflow (the Live copy by default) |
| `PATCH` | `/v1/workflows/{id}` | contributor+ | Update the Live copy (name, description, graph, or saved run defaults) |
| `DELETE` | `/v1/workflows/{id}` | contributor+ | Archive the workflow |
| `POST` | `/v1/workflows/{id}/versions` | contributor+ | Publish a version (freezes the Live copy) |
| `GET` | `/v1/workflows/{id}/versions` | viewer+ | List published versions |
| `POST` | `/v1/workflows/{id}/validate` | contributor+ | Check a graph without running it (a dry run) |
| `POST` | `/v1/workflows/{id}/command` | contributor+ | Start, pause, resume, or stop a run |
| `GET` | `/v1/workflows/{id}/runs` | viewer+ | List runs of this workflow |
| `GET` | `/v1/workflows/{id}/stream` | viewer+ | WebSocket stream of live run events |

When you `PATCH` a workflow you can send `base_revision` (the `revision` you last read). If someone else saved in between, the call fails with `409 revision_conflict` and saves nothing, so you never overwrite their work.

### Start, pause, resume, stop

`POST /v1/workflows/{id}/command`

```json
{
  "command": "start",
  "version": "live",
  "params": {
    "trigger_payload": {
      "topic": "weekly digest",
      "message": "Hello"
    }
  }
}
```

| Field | Description |
|-------|-------------|
| `command` | `start` (the default), `pause`, `resume`, or `stop` |
| `version` | What to run: `live` (the default), `published` (the newest published version), or a version number such as `3` |
| `params.trigger_payload` | The input for the run. Steps read it as `{{input.*}}` |
| `params.trigger_steps` | Optional per-step input overrides, keyed by step id |
| `params.run_id` | For `pause`, `resume`, and `stop`: the run to control |
| `params.mode` | For `stop`: `immediate` (the default) or `graceful` |

`start` returns `202 Accepted` with the new `run_id`, a `status`, and `ran` (which copy of the workflow ran). Keep the `run_id` to check progress.

### Runs and human tasks

| Method | Path | Role | Description |
|--------|------|------|-------------|
| `GET` | `/v1/runs` | viewer+ | Runs across the workspace (the data behind Command Center) |
| `GET` | `/v1/workflows/{id}/runs/{runID}/summary` | viewer+ | Current status of one run |
| `GET` | `/v1/workflows/{id}/runs/{runID}/events` | viewer+ | Step-by-step event log |
| `GET` | `/v1/workflows/{id}/runs/{runID}/context` | viewer+ | Run input and step results |
| `GET` | `/v1/tasks/pending` | viewer+ | Human tasks waiting for a decision, across the workspace |
| `GET` | `/v1/workflows/{id}/runs/{runID}/tasks/pending` | viewer+ | Waiting tasks for one run |
| `POST` | `/v1/workflows/{id}/runs/{runID}/tasks/{task_id}/complete` | contributor+ | Approve or reject a task |

Complete-task body:

```json
{
  "approved": true,
  "result": {
    "comment_body": "Optional fields merged into the step result"
  }
}
```

The step result always includes `approved`. The Console **Approve** and **Reject** buttons send only `{ "approved": true }` or `{ "approved": false }`. See [Human tasks](/workflows/human-tasks#what-downstream-steps-receive).

### Run event types {#run-event-types}

`GET /v1/workflows/{id}/runs/{runID}/events` returns these `event_type` values. See also [Runs and Command Center](/workflows/runs-and-command-center#failure-handling).

| `event_type` | Description |
|--------------|-------------|
| `step_started` | A step began |
| `step_completed` | A step succeeded, or was skipped (`data.skipped: true`) |
| `step_failed` | A step failed; the run may move to `failed` |
| `step_cancelled` | A step was still running when another step failed the run |
| `state_changed` | The run changed status |
| `run_started` / `run_rejected` | Run lifecycle |

## Inbound webhooks

Inbound webhooks let another system start a workflow run. See [Inbound webhooks](/integrations/inbound-webhooks) for setup and for how to sign requests.

| Method | Path | Role | Description |
|--------|------|------|-------------|
| `POST` | `/v1/inbound-webhooks` | contributor+ | Create a subscription |
| `GET` | `/v1/inbound-webhooks` | viewer+ | List subscriptions |
| `PATCH` | `/v1/inbound-webhooks/{id}` | contributor+ | Change what a subscription runs (Live, published, or a version) |
| `DELETE` | `/v1/inbound-webhooks/{id}` | contributor+ | Delete a subscription |
| `POST` | `/v1/inbound-webhooks/{subscription_id}` | Signature | Public ingress: the sender calls this to start a run |

Create a subscription:

```json
{
  "workflow_id": "workflow-uuid",
  "name": "form-leads",
  "automation_pat_id": "optional-existing-api-key-id",
  "automation_bearer": "pat_…"
}
```

The response includes `ingress_url`, `signing_secret` (shown once), and the `subscription`.

The sender does **not** use a token. Each ingress request needs:

- `X-Agentruntime-Signature: t=<unix seconds>,v1=<hex HMAC-SHA256>`, signed with the `signing_secret`
- `Idempotency-Key: <unique id per event>`, so retries do not start duplicate runs
- `Content-Type: application/json`

## MCP servers and instances

An **MCP instance** is a tool server (such as Postgres or GitHub) installed in your workspace. See [MCP instances](/integrations/mcp-instances) and [Custom MCP servers](/integrations/custom-mcp-servers).

Read calls (`GET`) are **viewer+**. Create and update calls (`POST`, `PATCH`) are **contributor+**. Delete calls are **project_admin**.

### Catalog and servers

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/v1/mcp/platform-catalog` | The built-in connector catalog |
| `GET` | `/v1/mcp/tools` | Tool catalog |
| `GET` | `/v1/mcp/servers` | Your workspace's MCP servers |
| `POST` | `/v1/mcp/servers` | Register a custom server |
| `GET` | `/v1/mcp/servers/{id}` | Server detail |
| `GET` | `/v1/mcp/servers/{id}/discover` | Discover the server's tools |
| `POST` | `/v1/mcp/servers/{id}/versions` | Publish a server version |
| `POST` | `/v1/mcp/servers/{id}/validate` | Run validation checks |
| `POST` | `/v1/mcp/servers/{id}/connections/{connection_id}/validate` | Check that a connection works with a server |

### Instances and config profiles

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/v1/mcp/instances` | List instances |
| `POST` | `/v1/mcp/instances` | Create an instance |
| `PATCH` | `/v1/mcp/instances/{id}` | Update an instance |
| `GET` | `/v1/mcp/instances/{id}/config-profiles` | List config profiles |
| `POST` | `/v1/mcp/instances/{id}/config-profiles` | Create a config profile |
| `PATCH` | `/v1/mcp/instances/{id}/config-profiles/{profile_id}` | Update a profile, including which connection it uses |

## Analytics

All analytics endpoints are `GET` and **viewer+**. They accept `window=month|week|all`, or bounded `from` and `to`. Time-series endpoints also accept a granularity. See [Analytics](/platform/analytics).

| Endpoint | Metric |
|----------|--------|
| `/v1/analytics/live-runs` | Runs in progress now |
| `/v1/analytics/success-rate` | Run success percentage |
| `/v1/analytics/execution-duration` | Wall-clock run time |
| `/v1/analytics/runs-count` | Runs in the window |
| `/v1/analytics/steps-executed` | Metered workflow steps |
| `/v1/analytics/credits-consumed` | Credits used in the window |
| `/v1/analytics/steps-summary` | Step-type breakdown and latency |
| `/v1/analytics/runs-timeseries` | Run count over time |

## Personal access tokens

Most people create tokens in the Console under **Settings → API keys**. These endpoints do the same from code.

| Method | Path | Role | Description |
|--------|------|------|-------------|
| `GET` | `/v1/pats` | viewer+ | List tokens (no secrets) |
| `POST` | `/v1/pats` | contributor+ | Create a token |
| `GET` | `/v1/pats/{id}/reveal` | project_admin | Show a stored token again |
| `DELETE` | `/v1/pats/{id}` | contributor+ | Revoke a token |

A token can never do more than the person who created it.
