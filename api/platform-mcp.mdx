title: Platform MCP
description: Let Claude, ChatGPT, Cursor, or another AI assistant build and run AgentRuntime workflows for you.

**Platform MCP** is a connection that lets an AI assistant work with your AgentRuntime workspace. Once it is connected, you can ask things like "list my workflows", "build a workflow that emails me a daily summary", or "start the weekly report and tell me when it finishes". The assistant uses AgentRuntime tools instead of you writing API requests.

This page is for people who use an AI assistant (Claude, ChatGPT, Cursor, Claude Code, and similar) and want it to manage AgentRuntime. **MCP** (Model Context Protocol) is the standard way assistants plug into tools.

| | |
|---|---|
| **Server URL** | `https://mcp.agentruntime.io/mcp` |
| **Sign-in** | Your AgentRuntime account (Claude, ChatGPT), or a personal access token |
| **Transport** | Streamable HTTP |

<Warning>
  Platform MCP is not the same as the **MCP instances** you add under **MCP** in the Console. Those are connector tools (Gmail, Postgres, and so on) that workflow steps call while a run is executing. Platform MCP controls AgentRuntime itself from your assistant.
</Warning>

## Connect Claude or ChatGPT

<Steps>
  <Step title="Add a custom connector">
    In Claude or ChatGPT, open the connectors settings and add a custom connector. Use the server URL `https://mcp.agentruntime.io/mcp`.
  </Step>
  <Step title="Sign in">
    The assistant sends you to an AgentRuntime sign-in page. Sign in with your usual account. If you belong to more than one workspace, choose the one to use.
  </Step>
  <Step title="Check it works">
    Ask the assistant to run `ar_get_started`. **What you should see:** your workspace name and projects, plus suggestions for what to do next.
  </Step>
</Steps>

You do not create or paste a token with this method.

## Connect with a token

Use a token for tools that cannot sign in, and for scripts.

<Steps>
  <Step title="Create a token">
    In the [Console](https://console.agentruntime.io), open **Settings → API keys** and click **Create API key**. Pick the **Run workflows** template, or choose scopes yourself (see [Scopes](#scopes-for-a-token)). Copy the token. It is shown once.
  </Step>
  <Step title="Add the server to your assistant">
    For Cursor, add a remote server in the MCP settings:

    ```json
    {
      "url": "https://mcp.agentruntime.io/mcp",
      "headers": {
        "Authorization": "Bearer pat_YOUR_TOKEN"
      }
    }
    ```

    Claude Code, Codex, and other clients that support remote HTTP servers use the same URL and header.
  </Step>
  <Step title="Check it works">
    Ask the assistant to call `ar_get_started` or `workflows_list`.
  </Step>
</Steps>

A token already belongs to one workspace, so you do not set a workspace header.

## Scopes for a token

A token only lets the assistant do what its scopes and your role allow.

| You want the assistant to… | Scopes |
|----------------------------|--------|
| Look around: list workflows and runs | `workflow:read` |
| Run workflows | `workflow:read`, `workflow:run`, `mcp:execute` |
| Build and edit workflows | add `workflow:edit` |
| Browse and set up connectors and connections | `mcp:read`, `mcp:write` |
| Manage agents | `agent:read`, `agent:write` |
| Read analytics | `analytics:read` |
| Complete approval tasks | `task:complete:agent_review` or `task:complete:on_behalf` |

If a tool fails with `403`, the token is missing a scope or your role is too low. See [API authentication](/api/authentication).

## Work in more than one workspace

When you connect by signing in, the connection works in one workspace at a time. Ask the assistant to list your workspaces (`ar_workspaces_list`) and switch (`ar_workspace_switch`). The switch applies to your next request. A connection made with a token cannot switch, because the token belongs to one workspace.

## What the assistant can do

The assistant sees these tools. You do not need to remember the names. Describe what you want in plain words.

### Get started and find your way

| Tool | What it does |
|------|--------------|
| `ar_get_started` | Run this first. It returns your workspace, projects, what you may do, and a recommended plan for common jobs |
| `ar_workspaces_list`, `ar_workspace_switch` | List your workspaces and switch (sign-in connections only) |
| `projects_list` | List your projects |
| `ar_builtin_tools_list` | List the built-in tools workflows can use |

### Workflows

| Tool | What it does |
|------|--------------|
| `workflows_list`, `workflows_get` | List workflows and read one |
| `workflows_create`, `workflows_update` | Create a workflow and edit its Live copy. Saves take effect at once |
| `workflows_archive` | Archive a workflow |
| `workflows_validate` | Check a workflow without running it |
| `workflows_graph_schema`, `workflows_authoring_contract`, `workflows_llm_step_contract` | Give the assistant the rules for writing valid steps |
| `workflows_publish_version`, `workflows_list_versions` | Freeze the Live copy as a numbered version, and list versions |
| `workflows_list_revisions`, `workflows_restore_revision` | See the save history and put an earlier save back |
| `workflows_package_update_preview`, `workflows_package_update`, `workflows_package_install_update` | Update a workflow you installed from the marketplace |

### Run, wait, and approve

| Tool | What it does |
|------|--------------|
| `workflow_run` | Start a run, and optionally wait for it |
| `workflow_await` | Wait for a run that is already going |
| `workflow_inspect` | Read what a run did and what it is waiting for |
| `workflow_approve` | Approve or reject a waiting human task, after you have seen it |
| `workflows_execute_command` | Lower-level start, pause, resume, and stop |
| `workflows_list_runs`, `runs_list_tenant`, `runs_get_summary`, `runs_list_events`, `runs_get_context` | Read run lists, status, events, and results |
| `tasks_list_pending`, `tasks_list_pending_run`, `tasks_complete` | List and complete human tasks |
| `workflows_stream_websocket` | Read a short window of live events from a run |

A run that reaches a human step stays **running** until someone completes the task. After starting a run, ask the assistant to check for waiting tasks before it reports success.

### Connectors, connections, and MCP servers

| Tool | What it does |
|------|--------------|
| `catalog_connectors_browse`, `catalog_tools_search`, `catalog_tools_schema` | Browse connectors and find the right tool |
| `catalog_instances_*` | List, create, update, and archive MCP instances, and connect them to a connection |
| `catalog_connections_*`, `connections_google_*`, `connections_whatsapp_*` | Create and manage connections, including Google and WhatsApp |
| `catalog_servers_*` | Register and validate your own MCP servers |
| `catalog_config_profiles_*` | Manage instance config profiles |

### Databases, apps, files, and packages

| Tool | What it does |
|------|--------------|
| `tenantdata_*` | List and create workspace databases, and migrate their schema |
| `surfaces_*` | Build and publish apps |
| `files_*` | List, upload, and download work files |
| `marketplace_*` | Plan and apply installs of marketplace packages, and publish your own |

### Webhooks, analytics, and keys

| Tool | What it does |
|------|--------------|
| `inbound_webhooks_list`, `inbound_webhooks_create`, `inbound_webhooks_update`, `inbound_webhooks_delete` | Manage inbound webhooks |
| `analytics_live_runs`, `analytics_success_rate`, `analytics_execution_duration`, `analytics_runs_count`, `analytics_steps_executed`, `analytics_credits_consumed`, `analytics_runs_timeseries`, `analytics_usage_timeseries` | Read analytics |
| `pats_*`, `llm_provider_keys_*` | Manage API keys and LLM provider keys |

<Note>
  Tools that create or reveal secrets (new API keys, webhook signing secrets, LLM provider keys, connection credentials) are sensitive. They may be turned off in your workspace's Platform MCP. If the assistant says a tool is not available, use the Console for that task.
</Note>

## Which copy of a workflow runs

Each workflow has one editable **Live** copy, plus optional numbered **published versions**. By default, assistant-started runs use Live, so a change the assistant saves is used on the next run, with no publishing step. The assistant reports what ran. Publish and pin a version only when something (a webhook, another workflow) must keep running a stable copy.

## Example requests

- "List my workflows and show the three most recent runs."
- "Check the daily report workflow for errors, then start a run with `{ "env": "staging" }`."
- "How many credits did my project use this week?"
- "Build a workflow that checks my Postgres database every morning and emails me a summary. Validate it before running."

## Common problems

| Problem | What to do |
|---------|------------|
| The assistant cannot sign in | Try again from the connector settings, or connect with a token instead |
| `403` or "insufficient scopes" | Add the missing scope to the token (see [Scopes](#scopes-for-a-token)) |
| It shows the wrong workspace | Ask it to list workspaces and switch (sign-in connections only) |
| A run never finishes | It is probably waiting on a human task. Ask the assistant to list pending tasks |
| An MCP step in a run fails | The instance may not be connected. Ask the assistant to check the instance's connection, or see [MCP instances](/integrations/mcp-instances) |

## Stay safe

- Use a dedicated token for each assistant, so you can revoke it without affecting other automation.
- Give it only the scopes it needs.
- Review what the assistant plans before it approves human tasks or changes production workflows.
- Revoke any token that appears in logs or shared configuration.
