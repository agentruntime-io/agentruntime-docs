AgentRuntime has three ways to prove who you are. Which one you use depends on what you are doing.

| I want to… | Use | Section |
|------------|-----|---------|
| Use the Console in my browser | Email and password, or Google | [Sign in to the Console](#sign-in-to-the-console) |
| Call the REST API from a script, CI job, or app | A personal access token (PAT) | [Personal access tokens](#personal-access-tokens-pats) |
| Connect Claude, ChatGPT, or another AI assistant | Sign in with your AgentRuntime account, or a PAT | [Connect an AI assistant](#connect-an-ai-assistant) |

## Sign in to the Console

Go to [console.agentruntime.io](https://console.agentruntime.io) and choose one of:

- **Email and password.** New accounts must verify their email address before they can continue.
- **Google.** Sign in with your Google account.

If you forget your password, use the forgot-password link on the sign-in page. The Console keeps you signed in and refreshes your session automatically.
<Note>
  A workspace admin can set sign-in rules for members. If a sign-in option is missing, ask your workspace admin.
</Note>

## Personal access tokens (PATs)

A **personal access token** is a secret string, starting with `pat_`, that lets a script act as you with only the permissions you choose. It is the recommended way to call the REST API. The Console calls them **API keys**.

A token can never do more than you can. If your role is `project_viewer`, a token you create cannot start runs, even if you give it the `workflow:run` scope.

### Create a token

<Steps>
  <Step title="Open API keys">
    In the [Console](https://console.agentruntime.io), open **Settings**, then the **API keys** tab. Click **Create API key**.
  </Step>
  <Step title="Name it">
    Enter a **Name** that says what the key is for, for example `CI deploy`. You can add an optional **Description**.
  </Step>
  <Step title="Choose scopes">
    A **scope** is one permission the token has. Pick only what the script needs. Common choices:

    | Scope | Lets the token… |
    |-------|-----------------|
    | `workflow:read` | List workflows, runs, events, and pending tasks |
    | `workflow:run` | Start, pause, resume, and stop runs, and validate workflows |
    | `workflow:edit` | Create, change, and archive workflows |
    | `mcp:execute` | Run MCP tools. Needed together with `workflow:run` for workflows that have MCP steps |
    | `mcp:read` / `mcp:write` | Read, or change, connections, MCP servers, and instances |
    | `task:complete:agent_review` | Approve or reject a task as a designated approver agent |
    | `task:complete:on_behalf` | Approve or reject a task for a person who delegated it |
    | `webhook:manage` | Manage inbound webhooks |
    | `agent:read` / `agent:write` | Read, or change, agents |
    | `analytics:read` | Read analytics |
    | `billing:read` | Read usage and billing |

    The dialog shows the full list with a short description for each.
  </Step>
  <Step title="Create and copy the token">
    Click **Create key**. The token is shown **once**. Copy it into a secrets manager. If you lose it, revoke the key and create a new one.
  </Step>
</Steps>

**What you should see:** the new key appears in the **API keys** list with its name and scopes. The secret itself is never shown in the list.

### Use the token

Send the token in the `Authorization` header. The token already belongs to one workspace (and project, if you chose one), so you do not need to send a workspace header.

```bash
curl "https://api.agentruntime.io/v1/workflows" \
  -H "Authorization: Bearer pat_YOUR_TOKEN"
```

A `200` response with a list of workflows means the token works. A `401` means the token is wrong or revoked. A `403` means the token's scopes, or your role, do not allow that call.

### Look after your tokens

- Give each script its own token so you can revoke one without breaking the others.
- Choose the narrowest scopes that work.
- Never put a token in git or in code that runs in a browser.
- To revoke a token, open **Settings → API keys** and click **Revoke key**. It stops working immediately.

<Warning>
  If a token is exposed, revoke it straight away, create a new one, and check your recent runs for activity you do not recognize.
</Warning>

## Connect an AI assistant

[Platform MCP](/api/platform-mcp) lets an AI assistant work with your workspace. You can connect in two ways:

**Sign in with your AgentRuntime account (recommended for Claude and ChatGPT).** Add AgentRuntime as a custom connector with the URL `https://mcp.agentruntime.io/mcp`. The assistant opens a sign-in page. Sign in as you normally do, and choose a workspace if you belong to more than one. You do not need to create or paste a token. Claude and ChatGPT both support this.

**Use a PAT.** Any MCP client that can send an HTTP header can connect with `Authorization: Bearer pat_...`. Use this for scripts, CI jobs, and tools that do not support sign-in. See [Platform MCP](/api/platform-mcp) for setup steps.

When you connect by signing in, the connection works in one workspace at a time. To change it, ask the assistant to switch workspace. See [Platform MCP](/api/platform-mcp#work-in-more-than-one-workspace).

## Inbound webhook signatures

Systems that start runs through an [inbound webhook](/integrations/inbound-webhooks) do not use a PAT. They sign each request with the subscription's signing secret.

## Common problems

| Problem | What to check |
|---------|---------------|
| `401` on every call | The token is mistyped, revoked, or missing the `Bearer ` prefix |
| `403` on a call that should work | The token is missing a scope, or your role is too low. Compare against the [API reference](/api/reference) |
| Runs start but MCP steps fail | Add `mcp:execute` to the token |
| I cannot create a key | Only members who are allowed to create API keys can. Ask a workspace admin |
| The AI assistant shows the wrong workspace | Ask it to list your workspaces and switch, or reconnect |
