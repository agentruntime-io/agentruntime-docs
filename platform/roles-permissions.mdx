This page explains who can do what in AgentRuntime. It is for admins who assign access and for anyone who sees a "permission denied" message.

## The two layers

Access has two layers:

1. **Workspace role** — your role in the whole workspace. It controls team invites, billing and workspace policy.
2. **Project role** — your role inside one project. It controls what you can build and run there. This is the role most people use every day.

## Workspace roles

| Role | What you can do |
|------|-----------------|
| **Member** | Belong to the workspace. On **public** projects you get **Contributor** access automatically. |
| **Admin** | Manage team invites, billing settings, domain verification and workspace access policy. |
| **Owner** | Full workspace control, including billing ownership and promoting other admins or owners. |

A workspace email invite sets only the workspace role. It does not attach a project. After accepting, the person can use **public** projects as a **Contributor**.

In the API, the workspace admin role is called `tenant_admin`.

### What each project role can do

| Capability | Viewer | Contributor | Project admin |
|------------|:------:|:-----------:|:-------------:|
| View workflows and runs | ✓ | ✓ | ✓ |
| View billing and usage | ✓ | ✓ | ✓ |
| Create, edit and publish workflows | | ✓ | ✓ |
| Start, pause and stop runs | | ✓ | ✓ |
| Create and edit connections and MCP instances | | ✓ | ✓ |
| Delete workflows, agents and connections | | | ✓ |
| Manage project members | | | ✓ |

Changing a plan, adding credits and similar billing actions need a workspace **Admin** or **Owner**, not a project role. See [Billing and credits](/platform/billing-and-credits).

## Public and private projects

- **Public** — every workspace member can use it, as a **Contributor** unless you give them a different project role.
- **Private** — only members you add can see it. It is hidden from the project switcher for everyone else.

To change this, open the **⋮** menu next to the project in the project switcher, click **Project settings**, and use the **Project visibility** switch. To add people to a private project, use the **Members** tab in the same dialog.

Workspace **Owners** and **Admins** can open private projects they are not members of, but they get **read-only** access by default. To let them edit, go to **Settings → Team & Members** and turn on **Full access on private projects**, then click **Save policy**.

## Where to manage access

| Task | Where |
|------|-------|
| Invite someone to the workspace | **Settings → Team & Members** (Admin or Owner) |
| Change someone's workspace role | **Settings → Team & Members → Current members** |
| Change someone's project role | **Settings → Team & Members** with the project selected, or **Project settings → Members** |
| See your own roles | **Settings → My access** |

## Access for API keys

An API key (personal access token) can never do more than the person who created it. Both the person's project role and the key's **scopes** must allow an action.

| Scope | Allows |
|-------|--------|
| `workflow:read` | List and read workflows, runs and events |
| `workflow:run` | Start, pause, resume and stop runs, and validate workflows |
| `mcp:execute` | Let workflow runs call MCP tools |

Other scopes exist, for example for managing workflows, connections, agents and webhooks. See [API authentication](/api/authentication) for how to pick scopes. Create keys in **Settings → API keys**.

## Common problems

| Problem | What to try |
|---------|-------------|
| A project is missing from the switcher | It is private and you are not a member. Ask a project admin to add you. |
| A button is disabled or you see "permission denied" | Check your roles in **Settings → My access**, then ask an admin. |
| An admin cannot edit a private project | Add them to the project, or turn on **Full access on private projects**. |
| An API call returns `403` | Your project role or the key's scopes are too narrow. See [Troubleshooting](/platform/troubleshooting). |
