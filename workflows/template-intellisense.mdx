A **template** is a placeholder in double braces, such as `{{input.topic}}` or `{{steps.<step-id>.result.message}}`. At run time AgentRuntime replaces it with a real value: from the run's starting input, or from an earlier step's output.

**Template intellisense** is the helper in Studio's text fields. Type `{{`, search by step name or field, pick a suggestion, and Studio writes the correct path for you.

**Who this is for:** anyone who wants one step to use another step's output.

## Where you will see it

Suggestions appear in any text field that accepts templates: a step's **prompt**, tool arguments, the **Starting input** fields under **Setup → Manual**, and the **Skip when** field. A small variable icon (tooltip **Insert variable**) sits inside the field and opens the same list.

<Tip>
  Click **Variables** in the toolbar (under **More** in a narrow window) to open the **Variable reference**: a read-only list of the start inputs, run context, connection context, step outputs, and step inputs available in this workflow, each with a copy button.
</Tip>

## Use a suggestion

<Steps>
  <Step title="Open a template field">
    Click a field such as an **Agent** step's prompt, or a field under **Setup → Manual**.
  </Step>
  <Step title="Type {{">
    Type two opening braces. Suggestions appear while your cursor is inside an unfinished `{{ …` (before the closing `}}`).
  </Step>
  <Step title="Search in plain words">
    Keep typing a step name, a field name, or part of a path. For example `prepare news context message`.
  </Step>
  <Step title="Pick one">
    Click a row, or press **Enter** or **Tab**. Studio inserts the full variable and adds the closing `}}`.

    You should see something like `{{steps.f79e84fa-609c-485e-83f1-acb3db67f856.result.message}}`.
  </Step>
</Steps>

Each suggestion has two lines. The bold line is a friendly label, such as `Prepare news context · message`. The grey line is the exact text that will be inserted. The dot in the label is only for reading; you never type it.

| You type | Finds |
|---|---|
| `input` or `input.topic` | Start input |
| `prepare news` | Steps whose name matches |
| `prepare news context message` | Step name plus field |
| `message` | Fields named `message` on steps or start input |
| `steps.f79e84fa…` | A step by the start of its id |

When a field contains `{{…}}` blocks, Studio shows how many **variable(s) detected** under it.

## Two kinds of variables

### Start input: `{{input.*}}`

Values given when the run starts: from **Setup**, the API, or a webhook. If your workflow has an input schema, its fields appear in the suggestions.

```
{{input.topic}}
{{input.message}}
```

### Step output: `{{steps.<step-id>.result.*}}`

What an earlier step returned.

```
{{steps.505d4d95-dcb2-4a9f-a3a7-007c062898f4.result.message}}
```

- `<step-id>` is the step's **Step ID** (the UUID in the step's settings header).
- `.result.<field>` is a field in that step's output.

You can reach deeper into the output by hand, for example `{{steps.<id>.result.items.0.title}}`, even when the dropdown does not list every nested field.

## Step ID versus display name {#step-id-vs-display-name}

Every step has two names:

| Name | Where you see it | Use it in templates? |
|---|---|---|
| **Display name** | The title on the canvas, for example `Lua transform` | No. Use it only to search. |
| **Step ID** | The step's settings header | **Yes.** This is `<step-id>`. |

Graphs written by hand may use readable ids such as `fetch_leads`, and steps inside loops use short ids. Always use the step's `id`, never its `name`.

## Templates versus Lua {#mustache-vs-lua-steps}

| Where | Syntax | Example |
|---|---|---|
| Tool arguments, prompts, and other template fields | Dot paths inside `{{…}}` only | `{{steps.<step-id>.result.user_id}}` |
| Lua script | Dot or bracket, with the step id | `steps["<step-id>"].result` |

<Warning>
  `{{steps['Lua transform'].output.field}}` does not work. Brackets are not read inside `{{…}}`, a display name is not an id, and the field is `.result`, not `.output`. A dry-run reports `template_unresolved`, and a real run would send the literal `{{…}}` text to the tool.
</Warning>

Lua does not use `{{…}}` at all.

## What the suggestions come from

Studio builds suggestions from your workflow's input schema, the tools' output schemas, and your agents' output schemas. Where none is known, it falls back to common fields:

| Step | Fields often suggested |
|---|---|
| **Agent** | The agent's output schema fields, or `message` |
| **Tool (`mcp`)** | The tool's output properties, including nested ones |
| **LLM** | `text` |
| **Human** | `approved` |

## Defaults and optional values

Inside one `{{…}}`, a `|` means "or else":

| Template | Meaning |
|---|---|
| `{{input.field \| "default"}}` | Use `"default"` when `field` is missing or empty |
| `{{input.field \| omit}}` | Leave the key out when it is missing |
| `{{input.a \| steps.read.result.a \| omit}}` | Try `input.a`, then the step's `a`, then leave it out |

## Inside a For each loop

Inside a **For each** body, `{{item}}` and `{{index}}` (or `{{foreach.item}}` and `{{foreach.index}}`) give the current item and its position. They work at run time but are not in the suggestion list, so type them yourself.

## Tips

| Topic | Guidance |
|---|---|
| Valid syntax | One `{{`, a path, one `}}`. Broken text such as `{{input.topic{{input.topic}}}}` will not resolve. |
| Undo | **Ctrl+Z** restores the previous whole value of the field. **Ctrl+Shift+Z** or **Ctrl+Y** redoes it. |
| Check before you run | Run **Dry-run**. A malformed template is left as literal text at run time. |

## Common problems

| Problem | What to try |
|---|---|
| A value comes through as literal `{{…}}` | Use the step `id` and dot syntax, and make sure the step is in `depends_on`. |
| `{{input.email}}` fails a dry-run | Add `email` under **Setup**, or use `{{input.email \| omit}}`. |
| No suggestions appear | The cursor must be inside an unfinished `{{ …`. Click the variable icon instead. |
