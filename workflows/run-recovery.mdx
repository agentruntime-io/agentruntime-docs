---
title: Run recovery
description: What to do when a run fails, and what AgentRuntime recovers for you automatically.
---

**Who this is for:** anyone whose workflow run ended in an error.

**What you will do:** find the failing step, fix the cause, and start a new run.

## The short version

A run that fails is **finished**. You cannot resume it or retry it from the failed step. Fix the cause, then start a **new run**. The new run starts from the beginning and gets a new run ID. The failed run stays in your history.

| Action | Available? |
|---|---|
| **Pause** and **Resume** | Yes, while a run is running or paused |
| Retry a failed run, or continue it from the failed step | No |
| Start a new run | Yes |

## Fix a failed run

<Steps>
  <Step title="Find the failure">
    Open [Command Center](/workflows/command-center), click the **Issues today** chip, and click **View** on the run. Or open the workflow in Workflow Studio and pick the run under **Run logs and metrics**.

    You should see one step marked **Failed**. The run's reason (for example **MCP tool error**, **LLM request failed**, or **Insufficient credits**) is shown in Command Center.
  </Step>
  <Step title="Read the error">
    Click the failed step in the **Events** tab and read its error message. Steps marked **Cancelled** or **Skipped · Blocked** are only a result of the failure; see [Runs and observability](/workflows/runs-and-command-center#failure-handling).
  </Step>
  <Step title="Fix the cause">
    Common causes: a wrong model or provider key, a connection that needs reconnecting, wrong tool arguments, or no credits. See [Troubleshooting](/platform/troubleshooting#a-run-failed).
  </Step>
  <Step title="Start a new run">
    Click **Run** in Workflow Studio. If a schedule or webhook should use your fix, check that it runs **Live** or the version you changed. See [Live copy and published versions](/workflows/studio#live-copy-and-published-versions).
  </Step>
</Steps>

<Note>
  A failed step is not retried (the `retry_count` field in the graph schema is not used by the runtime), so a step that fails, for example on a temporary tool error, fails the run. If the failure was temporary, start a new run.
</Note>

## What AgentRuntime recovers for you

Sometimes the process running a step is lost, for example during a restart on our side. AgentRuntime notices and decides what is safe to do, up to three times for one step:

| Step type | What happens |
|---|---|
| **Lua**, **LLM**, **Human** | The step runs again from the start |
| **Agent** | The agent continues from its last saved point. At most the tool round that was in progress runs again. |
| Tool (`mcp`), **Workflow**, **External agent** | The step is marked failed. A tool call or another run may already have had an effect, and running it again could repeat it. |
| **For each**, **While** | The loop runs again only if every step in its body can safely run again |

Because a step can occasionally run twice, design steps that change data so that repeating them is harmless, for example by including an order number in the tool arguments so a duplicate is ignored.

## Agent runs that stop without an outcome

An agent that hands work to other agents can stop without handing off or finishing. By default the run then asks a person to continue; you can choose to fail the run instead. See [Autonomous episodes](/workflows/autonomous-episodes#when-an-agent-stops-without-handing-off).

## Common problems

| Problem | What to try |
|---|---|
| The new run fails in the same place | The cause is not fixed yet. Read the error again, and check that the trigger runs the version you edited. |
| You need the data the failed run already produced | Open the run's **Events** tab and expand each finished step to see its **Output**. Outputs of steps that finished before the failure are kept. |
| A run is waiting, not failed | Check **Needs you** in Command Center. |
